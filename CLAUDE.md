# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Purpose

Automated daily market intelligence pipeline (for Americhem) that replaces a Moody's News Edge subscription. Scrapes open-web news, applies LLM synthesis, and delivers a BLUF-formatted HTML email to stakeholders.

## Commands

```bash
# Install dependencies
pip install -r requirements.txt

# Copy and populate environment variables before running locally
cp .env.example .env

# Run the full pipeline manually (ingestion then delivery)
python ingestion_engine.py
python delivery_engine.py

# Run all tests
pytest tests/

# Run a single test
pytest tests/test_report.py::test_name
```

Two GitHub Actions workflows exist:

- `.github/workflows/market_pulse.yml` — production schedule, runs ingestion then delivery Monday–Friday at 10:00 UTC; also dispatchable manually.
- `.github/workflows/market_pulse_test.yml` — manually-dispatched sandbox run. Sets `MARKET_PULSE_RUN_MODE=test`, routes mail to the `TEST_RECIPIENT_EMAILS` secret (Jason-only QA pool), and exposes `run_ingestion` / `send_email` input flags so you can re-render against existing rows without re-billing APIs. With `run_ingestion=false` no same-day test-mode macro-summary row exists (ingestion writes it), so `fetch_macro_summary` uses the **production** row read-only whenever it out-ranks the test candidate — content-fullness first (`MacroSummary.has_content`; an accounting-only row from a zero-yield run never shadows a content-full one, in either direction), then strict recency (ties keep the test row — the date-rollover grace) — the QA email keeps the executive summary and citations, and the test write-back stays a no-op on production accounting. The fallback is one-directional: production never reads test rows.

## Architecture

`CONTEXT.md` is the companion glossary — the shared vocabulary for seams and domain terms (Insight, materiality, relevance thresholds, macro summary, relevance gate). Read it alongside this section when the naming matters.

The pipeline is two sequential scripts sharing a Supabase database, plus five seam modules — one owning suppression accounting, one owning every database call, one owning every structured LLM call, one owning the outbound email transport, and one owning how the ingestion engine consumes article-discovery providers — plus `insight.py` (the per-article schema: taxonomies, normalization, field readers), `macro_summary.py` (the once-per-run macro-summary schema — `insight.py`'s run-level twin), `scoring.py` (the relevance thresholds the report applies), `report.py` (the report model and the pure report-assembly decision pipeline), `prompts.py` (every LLM prompt the pipeline assembles), `config.py` (every runtime configuration read the engines make), `run_instant.py` (the one clock reading a run makes, plus its run mode — the frozen value both engines thread), `run_budget.py` (what one ingestion run may spend — the frozen value `execute_pipeline`'s loop asks at its two checkpoints), `targets.py` (the targets catalogue — the one parser of `targets.yaml`), and `renderer.py` (the pure email renderer — the report model in, the email HTML out):

**`config.py`** — Single module concentrating the two engines' runtime configuration reads: `mp_config()` (the cached `market_pulse_config.yaml` load, replacing the old per-engine `_load_mp_config` duplicates), `run_mode()` (read only by `run_instant.RunInstant.current()` — the engines take the run instant instead), `env_int()`, the ZoomInfo feature flags (`zoominfo_news_enabled` / `relevance_gate_enabled` / `store_discovery_metadata`), and `validate_environment(engine)`. The last is a fail-fast startup guard (driven by `REQUIRED_SECRETS`, raising `MissingEnvironmentError`) that each engine's `main()` calls before `execute_pipeline(run)` — a misconfigured cron crashes at t=0 instead of part-way through a run. It is **not** a Protocol seam: the Protocol seams (`llm`, `daily_intelligence_repo`, `mailer`, `zoominfo_client`) keep reading their own secrets at use time, and config only validates their *presence*. The pure `report`/`scoring`/`prompts` modules never import it — they take a plain config dict as a parameter (`prepare_report(..., report_config=...)`). Tests inject at the consumer (`patch("config.mp_config", ...)`) or set env vars; behavior is covered in `tests/test_config.py`.

**`run_instant.py`** — The **run instant** (`CONTEXT.md` holds the definition and the history): frozen `RunInstant(now, run_mode)` — naive-UTC `now` plus the run mode, i.e. the `daily_summaries` row key — with `run_date` / `min_summary_date` / `header_date` / `subject_date` / `test_mode` derived as properties. `RunInstant.current()` is the only clock / `config.run_mode()` read either engine makes: each `main()` calls it once and hands the value to `execute_pipeline(run)`, which threads it — ingestion to `_finalize_run(ctx, run)` → `generate_macro_summary(..., run=)`; delivery to `fetch_todays_intelligence(run)`, `fetch_macro_summary(run)`, `prepare_report(..., run=)` → `_update_delivery_summary_counts`, `send_email(html, run=)` and `_record_delivery(run)`. Effectful functions take the value; pure ones (`delivery_window`, `render_report`) take the one field the caller derives. Tests hand the engines `tests/conftest.py`'s `RUN_INSTANT` / `TEST_RUN_INSTANT` instead of flipping `MARKET_PULSE_RUN_MODE` or patching `datetime`; the value itself is covered in `tests/test_run_instant.py`. Two consequences worth knowing: a local operator in a non-UTC zone now sees UTC dates in the subject/header and in the summary-row key (they were local; on the UTC runner nothing changed), and the instant is **per process** — see the Key Invariants entry for the midnight-straddle caveat.

**`run_budget.py`** — The **run budget** (`CONTEXT.md` holds the definition): frozen `RunBudget(max_scrapes, deadline_seconds, tail_reserve_seconds, concept_demand_ahead, entity_at)` — the two hard limits (the scrape cap `MAX_DAILY_SCRAPES = 180`, the API-cost guard; the pipeline deadline `PIPELINE_DEADLINE_SECONDS = 1800`, the CI-timeout guard) plus the **tail reserve**, the slice of each held back for the concept/macro groups still ahead in `targets.yaml`. The constants live here, not in `ingestion_engine`. `RunBudget.for_targets(targets, *, max_scrapes=…, deadline_seconds=…, tail_reserve_seconds=…)` classifies each target once (`entity_at`) and derives `concept_demand_ahead` — suffix sums of concept demand (`results_per_entity` per concept target; element 0 is the total, 58 with current config), so the slot reserve at each entity target is only the demand *still ahead* and front-loaded Tier 1 concepts are never reserved twice; the clock reserve is the constant `TAIL_RESERVE_SECONDS = 360`. Two checkpoints return a **budget verdict** — `Proceed` / `SkipEntity(reason)` / `Stop(reason)`, frozen dataclasses mirroring the candidate outcome: `before_target(elapsed, scrapes_attempted, target_index)` applies the hard limits (so a target reached at the cap never spends discovery it cannot scrape) and then the tail reserve for entity targets (`scrape_slots` / `wall_clock`; a `SkipEntity` means don't *start* it — the reserve never cuts a started target, only a hard limit does); `before_candidate(elapsed, scrapes_attempted)` applies the hard limits only (`deadline` / `scrape_cap`). Time-agnostic and pure: the loop owns the stopwatch and passes `elapsed`; the value decides and never logs. `execute_pipeline(run, *, budget=None)` builds the default from the targets and rejects (`ValueError`, before any seam is touched) an injected budget built from a different-length list — the value is indexed by target position; tests pass limit overrides through the harness's `limits=` knob (`limits={"max_scrapes": 3}`), which builds the budget from the targets it resolves, instead of overwriting module constants. The loop body per target is `_run_target(target, ctx, providers, budget, elapsed) -> Optional[Stop]`, so `execute_pipeline` logs a `Stop` as either *before* a target (no discovery spent) or *mid-batch* (discovery spent, batch cut) with the limit values. **Behaviour change shipped with the value (2026-08-28):** the scrape cap used to be checked only per candidate, so a target reached at the cap still ran discovery (a Serper query, its candidates counted into `urls_discovered` → `screened_count`) before stopping at its first candidate; it now stops before discovery, so on a cap-bound day `screened_count` and the provider-yield `discovered` counters are lower by that target's candidates — a semantics change, not a yield drop, when comparing across the boundary. Tested directly in `tests/test_run_budget.py` (pure verdicts, no clock, no file reads); the shipped-config headroom guard against the real `targets.yaml` lives in `tests/test_targets.py`.

**`targets.py`** — The **targets catalogue** (`CONTEXT.md` holds the **Target** definition): the one parser of `targets.yaml`. `load_targets(path) -> list[dict]` maps the control file to the plain target dicts the loop runs (`parse_targets(text, *, source)` is the same parser over text already in hand — the loader is that plus its one file read) — entity targets (carrying the ZoomInfo id/flag and the resolution hints `domain` / `hq_country` / `hq_state`) and concept targets — and `build_query` assembles each target's Serper query. **Fail-fast on shape** (`TargetsError`, uncaught like `MissingEnvironmentError`): a file that is not valid YAML, an empty or non-mapping file, an entity without `name`, an unknown `search_mode`, a concept group without a non-empty `include_any`, a scalar where a list belongs, a non-integer discovery setting, a `zoominfo_company_id` that is neither null nor a positive integer, a Moody's platform identifier in any of the three term lists — the whole file, inactive entries included. `build_query` is assembly only: it emits every term it is given (until 2026-09-02 it dropped the Moody's identifiers silently; rejecting them is the loader's job). Policy (tier order, macro groups last) is pinned against the shipped file in `tests/test_targets.py`, not validated. Every reader goes through it: `ingestion_engine` (`from targets import load_targets`; the harness stub is unchanged), `scripts/enrich_targets.py` (an entity-only filter over it) and `scripts/probe_serper.py`. `scripts/sync_zoominfo_ids.py`'s line-level patcher reads through it too — its plan comes from `entity_entries(text, *, source)` (every **entity entry** in file order, active or not — `CONTEXT.md` holds the term; one walk yields both the targets and the entries, so the loader's whole-file verdict comes with it) — and is otherwise a comment-preserving *writer* and post-conditions its output through `parse_targets` (see the script's bullet); the macro-group keys copied into `market_pulse_config.yaml` stay a report lever under the parity test.

**`suppression_ledger.py`** — Pure in-process module owning the suppression reason taxonomy (7 ingestion-owned + 10 delivery-owned codes; `ALL_CODES` is the one ordered view, ingestion then delivery — the QA breakdown strip in `renderer._render_qa_debug_section` iterates it instead of a hand-copied list, so a new code gets its labeled row automatically), `SAMPLES_CAP = 10`, and the same-day-retry merge semantics. Owns the taxonomy's two faces: `SuppressionLedger`, the **side-tagged accumulator** both engines record into (a ledger only accepts codes its own side owns), and `SuppressionAccounting`, the **side-less reader** of what a stored `daily_summaries` row records — a stored row is merged and two-sided, so it has no owning side. `SuppressionAccounting.from_row(row)` is the *one* parser of the persisted shape: `SuppressionLedger.from_row(side, row)` is that reader plus a side tag (the tag is the side the caller is about to act as, not the side of the codes in the row), and `renderer`'s QA block reads the same value, so the merge path and the QA email cannot drift apart. Tolerant on purpose (the tolerances and their reasons are listed at the definition): the notable one is that an **uninterpretable count is dropped, not raised** — raising would skip a whole day's delivery accounting over one meaningless code, and crash the QA email that exists to show it. The reader is **not** capped — `SAMPLES_CAP` is a write policy — but it offers `recent()`, the FIFO display slice, so a renderer never re-implements the cap. Used by both engines; performs zero I/O.

**`daily_intelligence_repo.py`** — Single seam for every Supabase query the pipeline makes. One Protocol (`IntelligenceRepo`), two adapters (`SupabaseIntelligenceRepo` for prod, `InMemoryIntelligenceRepo` for tests). Reads swallow exceptions and return an empty sentinel; writes raise so silent write failures crash the cron loudly. Two reads are deliberately **strict** (raise): `require_delivery_state` and `fetch_since`, because a write depends on what they return. Callers do `from daily_intelligence_repo import _repo` and call `_repo()`; tests inject the fake at the consumer module — e.g. `monkeypatch.setattr("delivery_engine._repo", lambda: fake)`. The repo does not know about `SuppressionLedger` — the same-day-retry merge for delivery counts lives in `delivery_engine._update_delivery_summary_counts`.

**`llm.py`** — Single seam for every structured (JSON) OpenAI call the pipeline makes. One Protocol (`LLM`), two adapters (`OpenAILLM` for prod, `FakeLLM` for tests). The interface is `complete_json(*, system, user, temperature=None, context="") -> Optional[dict]`: it owns the OpenAI client, `OPENAI_MODEL`, the `response_format=json_object` request, and the response-envelope handling (`choices[0].message.content` extraction + `json.loads`). It does **not** own response *validation* — each caller validates the parsed dict itself, because the rules are domain-specific (relevance fields, executive bullets, free-form paragraphs). Failure contract: `complete_json` never raises; on a transport error, empty content, or unparseable JSON it logs and returns `None`, and each caller maps `None` to its own sentinel (`synthesize_insight` → `None`, `generate_macro_summary` → `False`, `synthesize_thematic_paragraphs` → `{}`). Callers do `from llm import _llm` and call `_llm()`; tests inject the fake at the consumer module — e.g. `monkeypatch.setattr("ingestion_engine._llm", lambda: FakeLLM(returns=...))`. The SDK-shape contract (model id, json format) is asserted once in `tests/test_llm.py`, not re-asserted in every caller test.

**`mailer.py`** — Single seam for the one outbound email transport (the **Mailer seam** entry in `CONTEXT.md` is the definition). One Protocol (`Mailer.send(message: EmailMessage) -> None`), two adapters (`ResendMailer` for prod, `FakeMailer` for tests); `EmailMessage` (`sender`, `recipients`, `subject`, `html`) is the frozen value that crosses it. The adapter owns *sending* — endpoint, the `SMTP_PASS` key (read at send time), payload shape, and the retry policy, whose constants live in `mailer.py`; the consumer, `delivery_engine.send_email(html, *, run)`, owns *addressing* and composition and calls `_mailer().send(message)`, so `delivery_engine` holds no transport knowledge and `execute_pipeline` never sees the seam. Under pytest an **autouse** fixture (`_inert_mailer` in `tests/conftest.py`) installs a `FakeMailer` as the process-wide mailer, so no test can reach Resend by omission — the production workflow's pytest step runs with the live secrets in its environment; consumer tests that assert on what was sent take the `fake_mailer` fixture (that fake plus the addressing env). The request shape and retry policy are asserted once, at the adapter, in `tests/test_mailer.py`; `tests/test_run_instant.py` also pins, structurally, that neither engine module makes an ambient clock or run-mode read.

**`insight.py`** — Pure module owning the per-article **Insight** schema: the value taxonomies (`VALID_SENTIMENT_TAGS`, `VALID_COMMERCIAL_SEGMENTS`, `VALID_SIGNAL_TYPES`, `VALID_ACTIONS`), `normalize(raw) -> Optional[dict]` (the clamp/default/validate rules that turn a raw LLM dict into a storable row; returns `None` if a required key is missing), `is_discard(raw)`, the field readers `effective_impact` / `commercial_segment` / `signal_type`, and the two **value** readers `source_domain` / `parse_timestamp` (one stored value, not a row — they live at the lowest pure module because their callers span layers: `daily_intelligence_repo`, a seam a pure module may not import, shares the timestamp parser, and `prompts` shares the domain reader). The row stays a plain dict (the shape the repo and renderer rely on) — this module concentrates the *knowledge* about it, not the format. `ingestion_engine.synthesize_insight` calls `normalize`; the field readers are consumed by `report.py`, `prompts.py` and `renderer.py`, which import them from `insight` directly (tests do the same — `delivery_engine` no longer re-exports them), and `parse_timestamp` also by `daily_intelligence_repo` and `zoominfo_client`, so one tolerance set covers every reader of a stored timestamp. The macro-summary schema (`dominant_condition` / `executive_bullets` / `macro_outlook`) is a separate structured output owned by its own run-level twin, `macro_summary.py` (below). Schema rules are tested directly in `tests/test_insight.py`.

**`macro_summary.py`** — Pure module owning the once-per-run **Macro summary** schema — the run-level twin of `insight.py`. Where `insight.normalize` turns a raw per-article LLM dict into a storable Insight row, `macro_summary.assemble_macro_content(parsed, *, source_pack, article_count) -> dict` turns the raw macro LLM dict into the storable content fields (`dominant_condition` with the `<3-articles → Low Signal` / else `Mixed / Watch` fallback, the Low-Signal third-bullet override, `executive_bullets`, `macro_outlook`, the `executive_sources` bullet+signal union in source-pack order, and the legacy `executive_summary` string). It composes the two public validators — `validate_executive_bullets` (exactly 3 ordered-label bullets; per-bullet citations cleaned against the pack) and `validate_macro_outlook` (per-signal valid `direction` / canonical `affected_segments` / **≥1 valid citation** — the deterministic materiality gate that drops uncitable signals; capped at `MAX_MACRO_OUTLOOK_SIGNALS`) — plus the private `_clean_citation_ids` helper (keep valid int ids, dedupe order-preserving, cap at `MAX_EXECUTIVE_BULLET_CITATIONS`, `bool` excluded). The vocabulary it enforces is imported from `prompts.py` (`VALID_MACRO_CONDITIONS`, `VALID_MACRO_DIRECTIONS`, `EXEC_BULLET_LABELS`, the caps) and `insight.py` (`VALID_COMMERCIAL_SEGMENTS`), never re-defined — prompt promises and validator checks stay one definition. Pure: no I/O, clock, or env reads. `ingestion_engine.generate_macro_summary` keeps only the effectful half (prompt build, the LLM call, and the `daily_summaries` upsert), calling `assemble_macro_content` for the content. The module owns the schema in **both** directions (as `suppression_ledger.py` does for suppression): `MacroSummary` is the **read face** — one stored `daily_summaries` row, read defensively and once. `delivery_engine.fetch_macro_summary` converts at the seam where the row leaves the repo and returns it, so report assembly, `ReportModel.macro_summary` and the renderer never hold raw jsonb and a `.get()` on this shape has nowhere to reappear. It exposes `legacy_text`, `condition` (the **one** `dominant_condition` → `macro_sentiment` → `""` precedence rule, which used to be spelled twice in `renderer.py` 130 lines apart), `bullets` / `outlook` / `sources` (the defensive reads that were `report.structured_exec_bullets` / `_extract_macro_outlook`), the composed `suppression` (a `SuppressionAccounting`), and `has_content` (which retired `delivery_engine._summary_has_content`). `screened_count` / `surfaced_count` stay **`Optional`** on purpose — they are the row's **recorded counts** (`CONTEXT.md` holds the definition): the value types the read without picking a fallback, and an absent count is shown as absent (the QA block's `?`, the subtitle's omitted clause), never replaced with a different quantity. The **display-segment remap is deliberately not here** — `report._display_mapped_outlook` adds it, because that is report display policy, not schema. `None` still means *no row found* (logged by the fetch); a row that exists but carries no brief is `has_content is False`. Tested directly in `tests/test_macro_summary.py`.

**`scoring.py`** — Pure module owning the relevance thresholds the report applies to an Insight's materiality. `Scoring.from_config(config)` resolves the configurable bands (`reporting.visible_impact_threshold` default 6, `supporting_impact_threshold` default 4) and exposes `is_visible(row)` / `is_weak_relevance(row)`; module-level `tier(row)` (CRITICAL ≤3 / STRATEGIC ≥8 / ROUTINE) and `is_legacy_critical(row)` use fixed edges. Builds on `insight.effective_impact` (the *what*); scoring is the *what it means for the report*. `report.assemble_report` constructs a `Scoring`; `delivery_engine` re-exports `tier` as `_alert_tier` for its run-summary log line, and `renderer` calls `is_legacy_critical` for the meta-strip badge. **Out of scope** (left where they are): the suppression policy's `enterprise_min_impact` (a suppression parameter) and `_sentiment_word`'s legacy directional-sentiment mapping (tone, not materiality). Tested directly in `tests/test_scoring.py`.

**`prompts.py`** — Pure module owning every LLM prompt the pipeline assembles (see the **prompt spec** entry in `CONTEXT.md`). Three builders — `insight_prompt(config, *, article_text, source_url, trigger_entity, category)`, `macro_prompt(articles)`, `thematic_prompt(groups)` — each return a frozen `PromptSpec` (`system`, `user`, `temperature`, `context`); callers splat it into the LLM seam with `_llm().complete_json(**spec.kwargs())`. Text assembly only: callers keep validation, `llm.py` keeps transport. Owns the single `ENGLISH_OUTPUT_RULE` (the old ingestion/delivery duplicate pair and its lockstep comment are gone) and the macro vocabulary (`VALID_MACRO_CONDITIONS`, `VALID_MACRO_DIRECTIONS`, `EXEC_BULLET_LABELS`, `MAX_EXECUTIVE_BULLET_CITATIONS`, `MAX_MACRO_OUTLOOK_SIGNALS`) that `macro_summary.py`'s validators import — prompt promises and validator checks are one definition. `macro_prompt` also promises the `macro_outlook` contract (the third output key) with `direction` from `VALID_MACRO_DIRECTIONS` and `affected_segments` from the canonical `insight.VALID_COMMERCIAL_SEGMENTS` labels, and reserves `MACRO_OUTLOOK_SOURCE_PACK_QUOTA` pack slots for `signal_type == "Macro"` rows. `macro_prompt` ranks and caps the articles itself and returns `MacroPrompt` with `source_pack` attached: digest `[n]` markers and pack ids come from one enumeration, so the citation contract holds by construction. RULE 4/5 of the insight prompt are assembled from `market_pulse_config.yaml` (`commercial_segments` / `signal_types`) with fallback lists, and RULE 6's template score band ("3 or 4" in production) plus RULE 7's uncertain-relevance score are **derived from `Scoring.from_config(config)`** via `low_exposure_score_band` (low = supporting threshold, high = one above, capped below visible) — a `supporting_impact_threshold` change moves the prompt's promise with the appendix floor instead of stranding template rows below it; assembly is `str.replace()`, never `.format()` — the base prompt's literal JSON braces are load-bearing (pinned by a test). RULE 1 carries an explicit **precedence** line (issue #72): a false entity match is `DISCARD` — never a RULE 6 low-exposure template and never a RULE 7 uncertain-relevance score; RULE 6's score sub-rule and RULE 7's "do NOT discard when uncertain" are both scoped to articles that *are* about the correct entity, so the honest-exit templates cannot become an always-legal dodge of the disambiguation verdict (pinned by `tests/test_prompts.py`). `python scripts/show_prompts.py` dumps the assembled prompts (with `system_fingerprint`) for offline rewording/diffing at zero API spend. Prompt-contract tests live in `tests/test_prompts.py`.

### Discovery & enrichment subsystem (ZoomInfo)

A second, feature-flagged article-discovery path that supplements Serper. All flags default **off** — production behaviour is unchanged until each is explicitly enabled, and the ingestion engine does not write the discovery-provenance columns until `STORE_DISCOVERY_METADATA` is truthy.

**`discovery.py`** — The discovery seam: how the ingestion engine consumes article-discovery providers (see the discovery-seam entry in `CONTEXT.md`). One Protocol (`DiscoveryProvider`: `name`, `eligible(target)`, `discover(target) -> list[dict]`, `gate(candidate, target) -> Optional[GateDecision]`), two production adapters, and an in-memory fake. `SerperProvider` (always eligible; owns `discover_urls` + the neutral `_serper_candidate` shape; never gates). `ZoomInfoProvider` (eligibility reads `config.zoominfo_news_enabled()` + a mapped `zoominfo_company_id` + `zoominfo_news`; `discover` delegates to `zoominfo_client`; **owns the ZoomInfo relevance gate** — loads `target_metadata.yaml` itself, once per run, gated by `config.relevance_gate_enabled()`, and returns a drop/keep decision the *consumer* applies so suppression accounting stays in the ledger). `FakeDiscoveryProvider` lets discovery be tested by injecting providers (`monkeypatch.setattr("ingestion_engine._discovery_providers", …)`) instead of patching `requests`. `ingestion_engine.discover_candidates(target, providers)` fans them in in registry order (Serper before ZoomInfo, so a Serper hit stores first and ZoomInfo's copy dedupes); provider_yield seeding, gate dispatch, and eligibility are all provider-list-driven — no `"serper"` / `"zoominfo"` literal in the consumer loop. Tested in `tests/test_discovery.py` (per-adapter behaviour) and `tests/test_zoominfo.py` (consumer fan-in via injected fakes). The `zoominfo_client` HTTP layer keeps its own `requests`-level tests — the seam is about how the *engine* consumes providers, not that client.

**`zoominfo_client.py`** — ZoomInfo company-news discovery client (the deep HTTP/extraction library behind `discovery.ZoomInfoProvider`). Company/news enrichment **only** — never calls a Contact API and never returns contact data. Auth priority: OAuth client-credentials (`ZOOMINFO_CLIENT_ID` + `ZOOMINFO_CLIENT_SECRET`, token cached in-process) → static `ZOOMINFO_BEARER_TOKEN` → none (warn, return `[]`). Endpoints are override-able via env vars so a published-path change never needs code. Every failure mode is swallowed to `[]` — a ZoomInfo outage degrades discovery instead of crashing the cron; no secret or token is ever logged. Per-entity eligibility (flag on + a mapped `zoominfo_company_id` + `zoominfo_news` not disabled) is enforced by `discovery.ZoomInfoProvider.eligible`; concept-mode targets carry no company id and are ineligible.

**`relevance_gate.py`** — Pure ZoomInfo false-positive suppressor (NOT a second entity resolver), applied by `discovery.ZoomInfoProvider.gate`. ZoomInfo candidates are already company-linked; `evaluate` drops one only when a curated `exclude_term` appears AND no identity term (canonical name / identity terms / manual aliases) rescues it — identity rescue is checked first, absence of identity text alone never drops. `load_target_metadata` is the only I/O and swallows read/parse errors to `{}`, so a missing or malformed companion file silently disables the gate. Gated by `ZOOMINFO_RELEVANCE_GATE_ENABLED`; suppression reason is `zoominfo_company_mismatch`.

**`target_enricher.py`** + **`scripts/enrich_targets.py`** — An offline, operator-run utility (not part of the daily cron) that populates `target_metadata.yaml`. `target_enricher.py` is a pure, mock-free transform (ZoomInfo raw response + prior metadata → proposed metadata: status, confidence, conservative de-suffixed identity/industry terms; no acronyms); the clock and all I/O live in the CLI. Run with `python scripts/enrich_targets.py`. `target_metadata.yaml` is **machine-managed** — the CLI header marks which fields are hand-editable; do not hand-edit the generated ones.

Two further operator scripts complete the enrichment review loop (also offline, not part of the cron):

- **`scripts/review_resolution.py`** — Prints a compact review table for a proposed `target_metadata.yaml` (target → resolved id, canonical_name, HQ country, primary industry). Flags (⚠) a row when the resolved `canonical_name` is blank, target and canonical share no token (likely wrong entity), or the industry is off-domain (`OFF_DOMAIN_INDUSTRIES` — software, hospitality, etc.); unresolved rows show (∅); flagged/unresolved sort first. HQ country is shown but never auto-flagged (many legit targets are non-US) — scan it by eye for regional-subsidiary mis-resolutions. Covered by `tests/test_review_resolution.py`.
- **`scripts/sync_zoominfo_ids.py`** — Bridges approved ids from `target_metadata.yaml` into `targets.yaml` (ZoomInfo *news discovery* reads `targets.yaml`, not the metadata companion). **Decides in the catalogue, locates by marks, inserts in the text**: the plan — which entities get which id — is composed from `targets.entity_entries` (active, id-less, resolved in an active metadata record whose status is `approved`/`verified`); the patcher joins each entry to its place in the text by `yaml.compose` line marks, walking only the groups the catalogue named, so it judges no value and re-decides no mode rule — `active`, id-less-ness, null-ness and which groups hold entities are the catalogue's verdicts. Every catalogue-legal spelling is therefore a fill (quoted names or keys, trailing comments, `active: True`, any key order, a `null` placeholder rewritten in place with its note, `<<:`-merged fields, a concept group's leftover `entities:` list). Its **one pre-condition is name parity** — the composed document must list the same names in the same order as the catalogue — and what a line patcher cannot edit is refused **before anything is patched**, exit 1, nothing written, no diff, always by name and line: a planned fill on a flow-style item, on an alias of an anchored entry, or with no key line after its first to anchor on. Comment-preserving line-level patch (insert, or rewrite in place; CRLF preserved); dry-run by default (prints a unified diff), `--write` applies. Both modes post-condition the result through `targets.parse_targets` as an oracle **independent of the patcher's placement** — it derives its expectation from the runnable targets, never from the patcher's report (the fill *rule* is shared on purpose: the oracle guards where an id lands, not whether it should): an input the loader already rejects, a patch that would not load, or one that does not load to the current targets plus exactly the fills the catalogue expects exits 1 with nothing written (a mismatch means a bug in the script and says so). Deliberately refuses `needs_review` rows, staying a review step rather than an auto-approval step. Covered by `tests/test_sync_zoominfo_ids.py`.
- **`scripts/probe_serper.py`** — Live Serper diagnostic (needs `SERPER_API_KEY`; ~4 credits per entity). Issues the production query shape (`targets.build_query`) for a handful of entities under several `tbs` windows (the pre-#63 `qdr:h24` vs. the documented `qdr:d`, `qdr:h`, and none) and prints a side-by-side table plus a CONFIRMED / NOT CONFIRMED / INCONCLUSIVE verdict. Written for the 2026-08-26 yield collapse (issue #63): the probe showed Google now reads `qdr:h24` as past-*hour*, so `discovery.serper_time_filter` expresses the window in whole days (`qdr:d`, `qdr:dN`) and never emits an `h` form. Re-run it if entity discovery yield ever collapses again with no repo change. Pure helpers covered by `tests/test_probe_serper.py`.

**`ingestion_engine.py`** — Scrape → Synthesize → Store

The per-candidate decision logic is the **candidate gauntlet** (see `CONTEXT.md`): `process_candidate(candidate, target, ctx) -> Stored | Suppressed(reason) | Error` runs steps 3–6 below for one candidate, mutating a `RunContext` (stats, provider yield, seen headlines, stored-articles buffer, and the immutable `SuppressionLedger` reassigned in place). `ctx.suppress()` pairs every ledger record with its provider-yield bump in one call — a gate cannot record without bumping (an unusable LLM response is `synthesis_failed`, mirroring `scrape_failed`; `stats["errors"]` counts store failures only). The run-level limits (deadline, scrape cap, tail reserve) are the **run budget** (`run_budget.py`, above), asked by `execute_pipeline`'s loop at its two checkpoints — there is deliberately no run-terminating *candidate* outcome; a `Stop` verdict breaks the loop to the one `_finalize_run(ctx)` teardown (log stats + provider yield, `generate_macro_summary`, then the **synthesis-outage guard**). Unit-tested with dict literals + monkeypatched seams in `tests/test_process_candidate.py`.

**The synthesis-outage guard.** `is_synthesis_outage(stats, breakdown)` is a pure predicate: true when zero articles were stored **and** every LLM synthesis call failed (`synthesis_failed >= SYNTHESIS_OUTAGE_MIN_ATTEMPTS`, currently 3, with zero `llm_discard` — a discard proves the LLM answered). `_finalize_run` raises `SynthesisOutageError` on that signature, **after** persisting the accounting-only row, and `main()` maps it to `sys.exit(1)`. The point is the exit code: the workflow's delivery step runs only on success, so a dead LLM turns the job red and sends **no** email, instead of silently delivering a no-news report. This exists because 2026-08-03 did exactly that — expired OpenAI credits, 98/98 synthesis calls rejected with HTTP 429, ~108 scrapes billed, a green run, and a "No significant market events" email that read as a quiet news day. Every failure on that path is swallowed by design (`llm.complete_json` returns `None` so a provider blip can't crash the cron), so the *absence* of output was the only remaining signal.

1. Loads `targets.yaml` through the **targets catalogue** (`targets.load_targets`, above) to get active targets — two modes: **entity** (one Serper query per company name) and **concept** (one combined OR query per group, gated by `active: true` at group level)
2. Gathers candidate URLs from up to **two discovery providers** via the `discovery.py` seam (`discover_candidates(target, providers)`): Serper.dev (always on) and, per-entity, ZoomInfo company-news enrichment (feature-flagged — see the discovery/enrichment subsystem below). Runs semantic deduplication (`rapidfuzz token_sort_ratio >= 88`) against headlines seen in the last 72 h before scraping. Serper results are truncated client-side to `results_per_entity` (the API returns pages of 10 regardless of `num`), and candidates on known-unscrapable domains (login-walled platforms, retail product pages — `UNSCRAPABLE_DOMAINS` / `UNSCRAPABLE_HOSTS`) are suppressed before any scrape with reason `unscrapable_domain`
3. Strips URL query parameters, computes SHA-256 hash → skips if already in DB
4. Extracts article markdown via Firecrawl; falls back to a direct-HTTP scraper on HTTP 402 (quota exhaustion); skips if below `min_article_length`. Each Firecrawl request runs under a 20-second wall-clock ceiling (`FIRECRAWL_WALL_CLOCK_TIMEOUT`) so a hung scrape can't eat the pipeline deadline
5. Calls OpenAI `gpt-5.4-nano` with article text; receives structured JSON including `headline`, `americhem_impact` (BLUF "so what"), `sentiment_score` (1–10, legacy directional), the relevance-upgrade fields `sentiment_tag` (Negative/Neutral/Positive), `americhem_impact_score` (1–10, **materiality** — independent of tone), `impact_rationale`, `commercial_segment` and `signal_type` (validated against the labels in `market_pulse_config.yaml`), and `recommended_action`. The model may return `{"americhem_impact": "DISCARD"}` to drop false-positive entity matches.
6. Upserts row into `daily_intelligence` table (unique constraint on `url_hash`)
7. After all articles are stored, calls `generate_macro_summary()` — a second OpenAI call that writes `executive_summary`, `macro_sentiment`, the structured `dominant_condition` / `executive_bullets`, `macro_outlook`, and `executive_sources` to the `daily_summaries` table (keyed on `run_date`). Ingestion accounting survives every run: when no summary can be generated (zero stored articles, or an unusable LLM response) it upserts an **accounting-only** row instead — `screened_count` + suppression breakdown/samples with the content columns omitted from the payload, so a same-day retry never wipes an earlier full summary (see the accounting-only entry in `CONTEXT.md`; requires migration 006). Each executive bullet may carry `citation_source_ids`. `macro_outlook` is the **Macroeconomic Outlook**: `{current_condition, signals:[{indicator, direction, americhem_implication, affected_segments, citation_source_ids}]}`, validated by `macro_summary.validate_macro_outlook` (via the pure `assemble_macro_content` transform) — each signal must have a valid `direction` (`VALID_MACRO_DIRECTIONS`), canonical `affected_segments` (`insight.VALID_COMMERCIAL_SEGMENTS`), and **at least one valid citation** (the deterministic materiality gate: an uncitable signal is dropped; no surviving signal → `macro_outlook` is `null`). `executive_sources` is the packed list of sources cited by at least one surviving bullet **or** macro signal — the union (`[{id, headline, url, domain, segment, score}]`). Delivery renders inline citation markers (bullets *and* signals share one numbering space) plus a "Sources" list at the bottom of the email. `macro_prompt` reserves up to `MACRO_OUTLOOK_SOURCE_PACK_QUOTA` source-pack slots for `signal_type == "Macro"` rows so the outlook always has citable sources.
8. Runs under the **run budget** (`run_budget.py`): the `MAX_DAILY_SCRAPES = 180` scrape cap and the `PIPELINE_DEADLINE_SECONDS = 1800` wall-clock deadline (keeps runtime inside the GitHub Actions 40-min job timeout), plus the **tail reserve**: once remaining scrape slots fall to the concept demand still ahead (`RunBudget.concept_demand_ahead` — sum of `results_per_entity` over the concept targets not yet run; 58 in total with current config) or remaining wall-clock to `TAIL_RESERVE_SECONDS = 360`, remaining *entity* targets are not started so the concept/macro groups at the bottom of `targets.yaml` always get their discovery pass (concept targets keep running until a hard limit fires). Both hard limits are checked before a target's discovery as well as before each candidate (the cap at target level is new as of 2026-08-28 — see `run_budget.py` above for the `screened_count` effect).

**`delivery_engine.py`** — Fetch → Format → Send

1. Queries `daily_intelligence` directly via `fetch_todays_intelligence(run)` for the **delivery window** (see `CONTEXT.md`): every row created strictly after the last recorded **production** delivery (`daily_summaries.delivered_at` on the most recent earlier `run_date`, read via `repo.fetch_last_delivery`). The pure `delivery_window(now, last_delivered_at)` picks the cutoff; only when no prior delivery is recorded (fresh DB, migration 007 not yet applied) does it fall back to the legacy wall-clock lookback (`FALLBACK_LOOKBACK_HOURS` = 24; 72 on Mondays). The anchor is production-only and strictly-earlier-day in every mode, so a QA re-render sees the rows production saw and a same-day retry re-sends the whole day's window. This replaced "rows created in the last 24 h" after issue #64: a 13:53 UTC late start on 2026-08-27 pushed that window past every row of the previous day. Does **not** use the `todays_intelligence` view at runtime
2. Calls `fetch_macro_summary(run)` to retrieve the executive summary written by ingestion — the latest row in the run's mode dated on or after `run.min_summary_date` (the date-rollover grace)
3. Renders a single-zone HTML email and sends it through the **mailer seam**: `send_email(html, run=run)` composes an `EmailMessage` (addressing from env, subject from the run instant) and the seam's production adapter delivers it via the Resend HTTP API, retrying transient statuses (policy and constants in `mailer.py`).
4. After the send succeeds, `_record_delivery(run)` stamps `delivered_at` on the run's `daily_summaries` row (keyed on the run instant's `run_date` + `run_mode`, so a test run never touches production accounting) — the anchor the next run's delivery window starts from. The stamp is `run.now`, the run's **fetch instant** (the one clock reading `main()` makes — `RunInstant.current()` — which `execute_pipeline(run)` threads through every fetch, write-back, send and stamp; see `run_instant.py` above), not the send time, so a row a concurrent ingestion writes between fetch and send stays inside the next window. A failed send leaves it unset, so the next successful email reaches back over the rows that never went out; a failed fetch never reaches it — `fetch_since` is a **strict read** (raises, like `require_delivery_state`), so a database outage is a red job with no email rather than a no-news email whose stamp hides the rows the outage concealed. The stamp itself is non-critical: a failed write is a logged warning, never a red job (the email is already out; a red job would invite a manual re-run and a duplicate email).

**`report.py`** — Pure module owning the **report model** (`ReportModel`, a frozen plain-data value — the data seam between report assembly and rendering), the **citation set** (`CitationSet` — the email's one citation numbering space, below), and `assemble_report(rows, macro_summary, config)`, the decision pipeline:

1. Runs `_apply_delivery_suppression()` — a deterministic seven-rule guardrail (product-listing URLs, job postings, generic market reports, unrelated-color results, exact and semantic headline duplicates, Enterprise / Cross-Segment low-impact). First match wins; counts and last-10 samples are recorded as the delivery-side suppression breakdown. Rule 1 (Enterprise below `enterprise_min_impact`, 7) has one exemption (issue #65): a row whose `americhem_impact` opens with a RULE 6 **low-exposure template** (`prompts.LOW_EXPOSURE_TEMPLATE_PREFIXES` — `Adjacent market` / `Limited direct exposure`; matched by `report._is_low_exposure_template`, case-insensitive prefix) is kept **while it scores below the visible threshold**, so the supporting band the prompt binds those templates to actually reaches the appendix. The exemption can only add appendix rows — an over-scored template row at or above visible is still dropped, never a card — and it cannot cost a segment-specific row its place through dedup either: rules 6/7 keep the first row seen and rows arrive impact-desc, so template rows are processed **after every non-template row** (a duplicate contest never goes to a template; `kept` is returned in input order). Config switch `delivery_suppression.enable_low_exposure_template_exemption` (default true) is the rollback.
2. Filters to rows the `Scoring` object (from `scoring.py`) marks visible — `scorer.is_visible(r)`, i.e. materiality `>= visible_impact_threshold` (default 6). Materiality is `insight.effective_impact()` (`americhem_impact_score` if present, else `sentiment_score`).
3. Groups visible rows by `commercial_segment`, defaulting missing values to Enterprise / Cross-Segment, then applies the **display-only segment merge** — `reporting.segment_display_groups` (display header → list of canonical labels) folds several canonical segments under one reader-facing header (shipped: `"Transportation — Vehicles"` merges `Transportation - Automotive` + `Transportation - Non-Automotive`; aerospace stays separate). The merge runs **after grouping and before the per-segment cap**, so the cap (5) governs the combined section — a merged group cannot balloon to 10 cards; overflow flows to the appendix exactly as a single segment's overflow does. The **taxonomy stays granular by design**: `insight.VALID_COMMERCIAL_SEGMENTS`, stored `commercial_segment`, prompts, and `macro_outlook` validation are untouched, so a merge re-splits later with zero re-classification. The map (`report._segment_display_map`) is applied at **model-assembly time** so renderers stay ignorant of it: the display label becomes the `groups` key (section header + synthesis category), the appendix rows' `commercial_segment` (copy-on-write — input rows never mutated), and the macro-outlook signals' `affected_segments` (deduping collisions; validation stayed canonical at ingestion). Empty/absent mapping = no merge (config-only rollback); unknown canonical labels are ignored.
4. Applies `max_visible_articles_per_segment` then `max_total_visible_articles` **only when they are configured** — `max_total_visible_articles` defaults to `null` (uncapped); production sets `max_visible_articles_per_segment: 5` (since 2026-07-17). An integer re-imposes the cap (a config-only rollback); capped-out rows flow into the Additional Articles appendix (step 5), never a visible card.
5. Selects the **optional-discovery appendix** (`ReportModel.additional_articles`): suppression-surviving rows scoring at or above the supporting threshold (code default 4; production sets **3** since 2026-08-03) that are not visible cards — the weak-relevance band plus visible-band rows capped out of their segment — ranked **non-template before template** (a row whose So-What opens with a RULE 6 low-exposure template — `report._is_low_exposure_template` — ranks after every non-template row whatever its score, so template rows fill the appendix only when there is room and are the first the cap pushes out; production data showed the cap binds daily and is decided within the score-4 tier by recency, where the macro-group template rows, stored last and so newest, would otherwise displace segment-specific rows) → impact-desc → recency-desc (`published_at`, else `created_at`) → normalized headline → `url_hash`, capped at `reporting.max_additional_articles` (default 10). It does **not** affect `surfaced_count` (visible cards only). **Behaviour change shipped with the shared timestamp parser (2026-09-03), Python 3.10 only:** the appendix's recency token and its rendered date now accept the fraction widths Postgres actually emits (it strips trailing zeros, so `10:44:12.500000` comes back as `10:44:12.5`, which `fromisoformat` rejects before 3.11 — the version CI and production run). Such a `published_at` used to fail the parse guard and fall back to `created_at` (the scrape time, i.e. today), ranking the row as brand new and rendering no date; it now ranks on its real publish date and shows it. Rows can therefore reorder within the appendix, and where the cap binds a row can change places across it. A 59-page render corpus on 3.10 showed exactly this and nothing else: 24 blank date cells filled, one row reordered, zero membership or visible-card changes. On 3.11+ the parser is a no-op and the corpus is byte-identical. Enterprise / Cross-Segment low-impact rows are dropped by suppression rule 1 before this step, so they never appear in the appendix — except the RULE 6 low-exposure template rows rule 1 exempts (step 1), which is how an "Adjacent market" row scored 3–4 lands here. Rows discovered by a category in `reporting.appendix_exclude_categories` (production: the seven `macro_*` groups, issue #73) are **excluded from the appendix only** — `report._partition_appendix_exclusions` splits them off before ranking, and each excluded appendix-band row is recorded in the ledger as `appendix_excluded_category` (count + sample). The macro groups exist to feed the Macroeconomic Outlook's source pack, not to produce headline rows; a macro-group row scored at or above the visible threshold is still a visible card, ingestion is untouched, and `tests/test_targets.py::test_config_appendix_exclusions_match_the_macro_groups_in_targets` pins the config list to the `macro_*` keys in `targets.yaml` so a new macro group cannot leak into the appendix unlisted. Empty/absent list = no exclusion (config-only rollback).
6. Folds the derived `below_impact_threshold` and `weak_relevance` counts into the ledger, so the model's ledger is the complete delivery-side accounting and the write-back consumes it verbatim. `weak_relevance` counts only weak-relevance rows shown **nowhere** (neither a visible card nor the appendix — e.g. pushed out by the appendix cap); `below_impact_threshold` is deliberately broader (every suppression-surviving below-visible row, including ones the appendix now displays).

`assemble_report` is pure and deterministic (no I/O, clock, or env reads; `config=None` means built-in defaults, never a file read); `rows == []` yields the `no_news` model variant. Tests exercise the whole pipeline with dict literals and zero patches, importing the suppression/grouping internals from `report` directly; `delivery_engine` imports only `ReportModel` / `assemble_report` from it (and `render_report` / `TEST_MARKER` from `renderer`).

**`renderer.py`** — The **renderer** (`CONTEXT.md` holds the definition): the pure email renderer, moved out of `delivery_engine` as one block. Two public names: `render_report(model, *, today_str, test_mode)` — the one entry point, the report model in, the email HTML out — which `delivery_engine.execute_pipeline` imports bare and calls between `prepare_report` and `send_email`, and `TEST_MARKER` (the `[TEST] ` spelling both the title and, via `send_email`, the subject use). Everything else is private: the brand constants and `_TEST_BANNER_ROW`, `_section_header_row` + `_section` + `_single_cell` (the shared full-width section header, the outer shell the four headed sections share, and the one-cell row three of them fill), the card (`_render_meta_strip` / `_render_card`, with `_sentiment_word` and the `_SENTIMENT_TAG_COLORS` / `_SENTIMENT_TAG_GLYPHS` maps), the section renderers in email order (`_render_exec_summary` → `_render_macro_outlook_section` → `_render_segment_watch_section` → `_render_additional_articles_section` with its `_appendix_*` readers → `_render_sources_section` → the test-mode `_render_qa_debug_section`), the citation pieces (`_render_citation_marker`, `_render_executive_bullets`, `_render_sources_footer`), `_link` (every link in the email — the `_safe_http_url` guard lives inside it, so an unsafe URL renders its text unlinked by construction, as a styled span or bare text per site), and `_render_no_news_email`. The QA block reads the run's counts and suppression accounting off the typed **`MacroSummary`** the delivery fetch built (the accounting is a `SuppressionAccounting` composed onto it), and asks the ledger for the display slice (`recent()`), so no second parser and no copy of the cap policy live here; its "Last N suppressed items" heading names `SAMPLES_CAP`. No section reads a raw stored row: `render_report` sees only the report model and the typed summary hanging off it. Two rules every section follows: **every interpolated data value is HTML-escaped, trusted or not** — the LLM prose (synthesis paragraphs, the legacy summary), the condition badges, segment labels, the schema-validated `sentiment_tag` / `signal_type`, the caller's date, the header's screened count and the QA block's counts and samples (whose `reason` is echoed raw by `label_for` for an unknown code) included — each coerced with `str()` first, so a non-string in a jsonb sample field cannot crash the QA email; the breakdown counts are ints by the time the renderer sees them and are escaped anyway, so the rule needs no per-site reasoning about types. Fifteen sites interpolated raw until 2026-08-29; `tests/test_renderer.py::test_every_interpolated_data_value_is_escaped` now pins the rule across the whole email — it poisons every string field, renders, and requires the raw marker nowhere and the escaped one everywhere — rather than site by site. And **every href passes `_safe_http_url`** (inside `_link`, the one place a URL becomes an anchor; an unsafe URL renders its text unlinked). Pure and deterministic — no clock, config, seam or logger: it imports only `report`, `scoring`, `suppression_ledger`, `macro_summary`, `insight` and the stdlib — the one pure module that also forgoes a logger (same model, same bytes, no side channel), pinned as the row that forgoes `logging` in `tests/test_purity.py`. `delivery_engine` keeps the effectful half — `prepare_report`, the fetches, the write-back, `send_email`, `_record_delivery`, and `_alert_tier` for its run-summary log line — so `execute_pipeline` reads fetch → prepare → render → send with each stage a call into the module that owns it. The two page shells are deliberately **not** unified (daily vs. no-news differ by design — header, subtitle strip and footer — so that is a layout decision, not a dedupe).

**Email layout — Commercial Segment Watch.** Rendering lives in `renderer.py` (above) and is one zone, produced by `_render_segment_watch_section()`. `execute_pipeline` makes **two calls** — `prepare_report(rows, macro_summary, run=run)` then `render_report(model, ...)` — composing three stages (see the report-model entry in `CONTEXT.md`):

1. `assemble_report()` (from `report.py`, above) produces the `ReportModel`. In production this runs **inside** `prepare_report`, which takes raw rows — there is no model-in/model-out effectful call; tests and QA scripts wanting a pure model call `assemble_report` directly.
2. The effects half of `prepare_report()` — the run's **single effectful step**, exactly once per delivery run, skipped entirely for the `no_news` variant: writes `surfaced_count` and the merged ingestion+delivery `suppression_breakdown` back to the run's `daily_summaries` row (keyed on the run instant) via `_update_delivery_summary_counts()` (idempotent on same-day retry), then fills `model.synthesis` via `synthesize_thematic_paragraphs()` (only `model.synthesis_candidates()` — the final capped groups with 2+ articles; `{}` on LLM failure, and only the string-valued entries of the answer are kept — the caller-validates half of the LLM-seam contract, so a drifted shape is bullets-only for that segment rather than a render-time crash).
3. `render_report(model, *, today_str, test_mode)` — **pure**: the clock and the `MARKET_PULSE_RUN_MODE` resolution belong to the caller (`execute_pipeline` derives both from the run instant — `run.header_date` / `run.test_mode`; the wiring is pinned by the delivery execute-pipeline tests). Dispatches on `model.variant` — the no-news email is a model variant, not a separate code path. A model whose `synthesis` is empty renders bullets-only; that *is* the fallback, so tests render unprepared models directly.

Between the executive summary and Commercial Segment Watch, `render_report` emits the **Macroeconomic Outlook** via `_render_macro_outlook_section(model.macro_outlook, citations)` — a one-line current condition plus one compact escaped row per material signal (indicator, colored direction, Americhem implication, affected segments, inline citation). Omitted entirely when `model.macro_outlook` is `None` or has no signals. Its citation markers share the email's single numbering space with the executive bullets, and the bottom "Sources" list covers both.

**Citation numbering — `report.CitationSet`.** The shared numbering space is a value, not a convention (see the **citation set** entry in `CONTEXT.md`). `CitationSet.from_summary(macro_summary, macro_outlook)` is the one place the rule is applied — number by first appearance, **executive bullets then macro-outlook signals**, only for ids resolving to an `executive_sources` entry — and it numbers the *renderable* outlook (`MacroSummary.outlook`, display-mapped by `report._display_mapped_outlook`), so the footer can never list a source no inline marker references. `assemble_report` builds it once and carries it on `ReportModel.citations`; `render_report` reads that one value and hands it to all three citation-bearing sections (`_render_exec_summary`, `_render_macro_outlook_section`, `_render_sources_section`), which no longer derive bullets/signals/sources of their own. The value owns the id→source index the four renderers each used to rebuild (`display_number` / `source` / `ordered`), and is falsy when nothing is numbered — the legacy identity: a row with no `executive_sources` renders no markers and no footer. `_render_executive_bullets` / `_render_sources_footer` keep their pre-existing `(sources, display_map)` parameters as a legacy spelling that constructs the same value. `tests/test_renderer.py::test_citation_numbering_is_one_space_across_bullets_signals_and_footer` pins the invariant by parsing both the inline markers and the footer rows out of the rendered HTML — both sides derived, nothing hand-copied.

Below Commercial Segment Watch (and above the Sources footer) `render_report` emits the **Additional Articles to Explore** appendix via `_render_additional_articles_section(model.additional_articles)` — a compact, escaped, `_safe_http_url`-guarded list (linked headline + segment / impact / source / date meta, **no** "So what" narrative; the date renders only from `published_at`, never the scrape timestamp). The section is omitted entirely when `additional_articles` is empty.

Each card is rendered by `_render_card(item)` (the single, shipped card renderer) and displays the `impact_score`, `sentiment_tag`, `signal_type`, BLUF "So what", and a `CRITICAL` badge when a legacy row is `scoring.is_legacy_critical()`. The "So what" label carries a **direction glyph** keyed by `sentiment_tag` (`_SENTIMENT_TAG_GLYPHS`: ▼ Negative / ● Neutral / ▲ Positive, colored from `_SENTIMENT_TAG_COLORS`) — the direction cue sits on the prose, where the reader's eye is, so a mis-spun sentence is visibly contradicted; rows with no recognized tag render no glyph. Shape carries the signal independently of hue, so red/green color-blindness does not lose it. The card shows **no** ACTION line — `recommended_action` is a suppression-policy override (job-posting escalation), not reader-facing copy; the segment is the block header, not an in-card badge. The old Critical Disruptions / Thematic Intelligence / Peripheral Signals zones have been removed (along with the pre-redesign `_render_card`/`_render_section` pair); integration tests still assert those section headers do not appear.

When `MARKET_PULSE_RUN_MODE=test`, both the subject line and the rendered HTML are marked: `[TEST]` prefix and an amber "TEST RUN · Jason-only QA output" banner row.

**Database** (`schema.sql`) — Two tables: `daily_intelligence` (articles) and `daily_summaries` (one macro summary row per run date). The `todays_intelligence` view adds an `alert_tier` column for ad-hoc queries; the unique index on `url_hash` is the deduplication gate.

`migrations/` holds incremental SQL applied via the Supabase SQL editor; each file is idempotent (safe to re-run). A fresh DB can initialize from `schema.sql` alone — it already contains the current columns; existing DBs must apply the migrations in order before running the matching code:

- `001_add_relevance_fields.sql` — relevance-upgrade columns (`sentiment_tag`, `americhem_impact_score`, `impact_rationale`, `strategic_segment`, `include_in_report`).
- `002_split_segment_and_structured_summary.sql` — splits `commercial_segment` from `signal_type`; adds the structured macro-summary fields (`dominant_condition`, `executive_bullets`), `run_mode` isolation, and suppression counts/samples.
- `003_add_discovery_metadata.sql` — multi-provider discovery provenance (`discovery_source`, `external_company_id`, `published_at`, `source_metadata`). **Rollout order matters**: merge the ZoomInfo code (flags off) → apply this migration → set `STORE_DISCOVERY_METADATA=true`.
- `004_add_executive_sources.sql` — `executive_sources` jsonb for citations. **Required, not flag-gated** — apply this migration *before* deploying the citation code, or ingestion upserts crash and delivery's summary blanks out.
- `005_add_macro_outlook.sql` — `macro_outlook` jsonb for the Macroeconomic Outlook section. **Required, not flag-gated** (same contract as 004) — apply *before* deploying the macro-outlook code, or `generate_macro_summary` upserts crash and delivery's summary blanks out. Stored `null` when no material signal exists.
- `006_relax_summary_content_nullability.sql` — drops `NOT NULL` on `executive_summary` / `macro_sentiment` so accounting-only rows (zero-yield runs, issue #43) can be inserted. **Required, not flag-gated** — apply *before* deploying the issue-#43 code, or the accounting-only upsert crashes the ingestion cron on exactly the runs it exists to record.
- `007_add_delivered_at.sql` — `delivered_at timestamptz` on `daily_summaries`, the delivery-window anchor (issue #64). **Degrades gracefully but apply first**: until the column exists the anchor read fails and is swallowed (wall-clock fallback) and the post-send stamp logs a warning — nothing crashes, but the late-start gap the migration fixes stays open.

**`targets.yaml`** — The first of two non-technical control files. Add/remove entities here; no Python changes required. Top-level keys:

- **Group order is the graceful-degradation policy.** `targets.load_targets()` processes groups top-to-bottom and execution follows file order, so a run that exhausts `MAX_DAILY_SCRAPES` or `PIPELINE_DEADLINE_SECONDS` mid-list drops whatever sits lowest. Groups are ordered by value in **four tiers** — highest survives first: **Tier 1** the eight priority commercial-segment concept groups (healthcare, fibers, building_construction, transportation_automotive, packaging, transportation_aerospace, transportation_non_automotive, engineered_resins — in that order); **Tier 2** the entity groups (competitors → customers → suppliers; customer order is preserved as-is because no authoritative priority-customer list exists in the repo); **Tier 3** the remaining concept groups (masterbatch_additives_innovation, performance_compounds, industry, europe_polymer_signals, asia_pacific_polymer_signals, electronics); **Tier 4** the macro groups (must stay last). When the budget runs out, macro is sacrificed first, then Tier 3, then entities, then the priority segments last of all. This ordering is insurance for heavy news days (the tail reserve in `run_budget.py` is the primary defense); relational invariants are pinned in `tests/test_targets.py`.
- `discovery.results_per_entity` / `lookback_hours` / `min_article_length` — discovery tuning (`results_per_entity` is the global default)
- **Entity-mode groups** (`search_mode: entity`): list entities under `entities:` as `{name, active}`; set `active: false` to pause without deleting
- **Concept-mode groups** (`search_mode: concept`): set `active: true/false` at the group level; define `include_any` (OR'd terms) and optional `include_all` / `exclude_any`. A concept group may also declare its own `results_per_entity` to raise (or lower) its discovery volume above the global default; the resolved value is stored on the target dict, so it flows into both `discover_urls` (client-side truncation) and the tail reserve's concept demand (`RunBudget.concept_demand_ahead`) automatically. The override is **concept-only** — a stray `results_per_entity` on an entity group is ignored. The eight **priority-segment groups** (healthcare, fibers, building_construction, the three `transportation_*` groups, packaging, engineered_resins) set it to **4** (vs. the global 2); macro groups deliberately stay at the global value so they don't inflate the tail reserve. Do not raise a priority group above 4 without re-measuring the `MAX_DAILY_SCRAPES` budget. Priority-segment group keys mirror the `commercial_segments` keys in `market_pulse_config.yaml` exactly. The old combined `transportation` group was split into `transportation_automotive` / `transportation_aerospace` / `transportation_non_automotive` to match those config sub-segments.
- **Macro groups** (`macro_manufacturing`, `macro_construction`, `macro_automotive`, `macro_consumer_demand`, `macro_inflation_rates`, `macro_energy_freight`, `macro_business_investment`): dedicated concept groups feeding the Macroeconomic Outlook. They **must stay last** in file order (Tier 4) — `load_targets()` processes groups top-to-bottom, so a deadline-limited run sacrifices macro coverage first, then Tier 3 concepts, then entities, then the priority segments (graceful degradation by the four-tier order above). The old generic `economic` group was absorbed here; do not reintroduce it.
- **Shape rules are enforced at load (`targets.TargetsError`, since 2026-08-28):** the file must be a mapping of groups with at least one active target; each group a mapping with `search_mode` `entity` or `concept`; every entity a mapping with a non-empty string `name`; `active` / `zoominfo_news` real booleans (a quoted `"false"` is rejected, not treated as true); `include_any` / `include_all` / `exclude_any` / `entities` lists; `discovery.*` and a group's `results_per_entity` integers; a concept group needs a non-empty `include_any`; an entity's `zoominfo_company_id` null or a positive integer (`targets.is_company_id`, the one spelling of "mapped" — the ZoomInfo provider's eligibility reads it too); none of the eight legacy Moody's platform identifiers (`_MOODY_PLATFORM_IDENTIFIERS`, e.g. `"source set 238658"`, `"PR wires"` — News Edge source names, never search terms; matched with case and surrounding whitespace folded) in any term list (these two since 2026-09-02). **The whole file is validated, inactive entries included** — a paused group with a blanked `include_any` fails the run at t=0 (previously it was skipped silently), so retire a group by `active: false`, not by emptying its terms. The offline scripts (`enrich_targets`, `probe_serper`) read through the same loader and fail the same way on a malformed draft file.

**`market_pulse_config.yaml`** — The second control file. Tunes the report and the LLM's segment taxonomy without code changes:

- `reporting.visible_impact_threshold` (default 6) — minimum `americhem_impact_score` for an article to appear as a visible card; raise if the report feels noisy.
- `reporting.supporting_impact_threshold` (default 4; production sets **3** since 2026-08-03, widening the appendix for quick-scan readers) — rows above this but below the visible threshold populate the Additional Articles appendix (the appendix band is "supporting threshold and above, not shown as a card" — weak-relevance rows plus cap overflow).
- `reporting.max_visible_articles_per_segment` (default `null` = uncapped; production sets **5**) and `reporting.max_total_visible_articles` (default `null`) — integer caps on per-segment / total visible cards. Capped-out rows flow into the Additional Articles appendix. Config-only, no code change.
- `reporting.max_additional_articles` (default 10; production sets **20** since 2026-08-03) — cap on the Additional Articles to Explore appendix.
- `reporting.appendix_exclude_categories` (default absent = no exclusion; production lists the seven `macro_*` groups since 2026-08-27, issue #73) — `targets.yaml` group keys whose rows never reach the Additional Articles appendix (appendix-only: visible cards and ingestion are untouched; the drop is ledgered as `appendix_excluded_category`). Exact keys, pinned to the `macro_*` groups by a parity test — add a macro group to `targets.yaml`, add it here too.
- `reporting.segment_display_groups` (default absent = no merge) — a mapping from a reader-facing header to the list of canonical `commercial_segment` labels folded under it. **Display-only, config-only rollback**: changes headers in the email without touching the LLM taxonomy or stored data (re-splittable with zero re-classification). Applied post-grouping / pre-cap so the per-segment cap governs the merged section. Unknown canonical labels are ignored. Ships merging the two ground-transportation segments into `"Transportation — Vehicles"` while `Transportation - Aerospace` stays its own section.
- `commercial_segments.<key>.label` / `description` — rendered into RULE 4 of the synthesis system prompt via `prompts._taxonomy_block()` (`signal_types` feed RULE 5 the same way). Editing *descriptions* is config-only and changes how the LLM classifies articles. Adding a **new** segment is NOT config-only: the label must also be added to `insight.VALID_COMMERCIAL_SEGMENTS` and `prompts._FALLBACK_COMMERCIAL_SEGMENT_LIST`, or `insight.normalize` silently rewrites the new label to Enterprise / Cross-Segment (the config↔code parity test pins this). Add new segments at the bottom; do **not** reorder keys. (`strategic_segments` is the pre-relevance-upgrade legacy block — no code reads it.)

## Tests

A test lives with the module whose **output** it asserts on: `tests/test_ingestion_engine.py` and `tests/test_delivery_engine.py` for the two engines, `tests/test_renderer.py` for `renderer.py` (a test that assembles a `ReportModel` only to render it is a renderer test — the HTML is the observable; a delivery test that reads HTML reads what crossed the mailer), `tests/test_report.py` for `report.py`'s pure decision pipeline (dict literals, zero patches), `tests/test_purity.py` for the **pure module** contract (CONTEXT.md holds the definition; the table in that file is the source of truth for which modules are pure, each scanned from its own AST), and `tests/test_targets.py` for `targets.py` (`load_targets` / `parse_targets` / `entity_entries` + `build_query`, including the shape-error rejections) plus every pin against the **real** control files (`targets.yaml`, `market_pulse_config.yaml`). Each file's docstring carries its inventory. The pure seam/schema modules are tested directly and in isolation — `test_insight.py`, `test_macro_summary.py` (the macro-summary validators + the `assemble_macro_content` transform), `test_scoring.py`, `test_run_instant.py` (the run instant's derived dates and its single effectful `current()`), `test_run_budget.py` (the run budget: the position-aware concept demand and both checkpoints' verdicts), `test_suppression_ledger.py`, `test_intelligence_repo.py`, `test_llm.py` (the SDK-shape contract, asserted once), `test_mailer.py` (the Resend request shape and the retry policy, asserted once at the adapter), `test_prompts.py` (the prompt contracts: English rule, RULE 4/5 config injection, macro digest↔source-pack id parity, the JSON-brace guard — no fakes, no patching), and `test_discovery.py` (the discovery seam: per-adapter eligibility / discover / gate behaviour, and the `FakeDiscoveryProvider` + `_discovery_providers()` registry). The discovery/enrichment subsystem has its own coverage — `test_discovery.py`, `test_zoominfo.py` (now exercising the consumer fan-in via injected fakes; the remaining `requests`-level patches all target the `zoominfo_client` HTTP layer), `test_zoominfo_company.py`, `test_relevance_gate.py`, `test_target_enricher.py`, `test_enrich_targets_cli.py`, and the operator-script tests `test_review_resolution.py` / `test_sync_zoominfo_ids.py`. All external API clients (OpenAI, Supabase, Resend, Serper, Firecrawl, ZoomInfo) are mocked or use the in-memory adapter — no live calls in the test suite.

**The shared pipeline harnesses.** Every test that drives an engine's `execute_pipeline` end-to-end goes through a fixture in `tests/conftest.py` that stubs the whole seam stack in one place. `run_ingestion_pipeline` (non-autouse, alongside the autouse `_reset_discovery_providers`) stubs `load_targets`, `discover_candidates`, `_hydrate_seen_headlines`, `url_already_processed`, `is_semantic_duplicate`, `scrape_article`, `synthesize_insight`, `store_insight`, `generate_macro_summary`, `time.sleep`; hands `execute_pipeline` the shared `RUN_INSTANT` (override with `run=`) and, when `limits=` is given, a `RunBudget` built from the targets it resolved (so an injected budget can never mis-index); and returns a frozen `PipelineRun(stored, macro)`. Pass exactly one target source: `targets=[...]` (patches `load_targets`) or `targets_yaml="..."` (writes `tmp_path/targets.yaml` and chdirs there, leaving the **real** `load_targets` to map it — the only way to exercise YAML-derived fields like `zoominfo_company_id`, and what makes the ZoomInfo gate tests' `target_metadata.yaml` resolve). Its delivery twin, `run_delivery_pipeline(fake_repo, *, run, llm_returns, report_config)`, injects the repo and a `FakeLLM` around `delivery_engine.execute_pipeline(run)` and returns the `fake_mailer` fixture's `FakeMailer` (its `sent` list is what crossed the seam). conftest also owns the suite's **shared builders** — one spelling of each shape, documented at the definition: `stub_insight` (the per-article LLM output), `stub_target` (a target dict as `load_targets` maps it), `stub_row` (a stored new-style `daily_intelligence` row), `stub_source` (an `executive_sources` entry), `stub_macro_signal` (a valid Macroeconomic Outlook signal), `stub_macro_llm` (the raw macro dict as the LLM returns it — what `assemble_macro_content` consumes), `stub_summary_row` (a stored `daily_summaries` row: the content fields plus the accounting columns every run writes), `stub_llm_insight` (a `FakeLLM` answering an insight), `stub_http_response` (a `requests.Response` stand-in), plus `appendix_hashes`, `VISIBLE_6_CFG` and `VALID_MACRO_OUTLOOK`. Test files add local `functools.partial`s over these for a section's defaults (e.g. `test_report.py`'s `_row`) rather than a second builder. `tests/test_pipeline_harness.py` keeps **both** fixtures honest in both directions: a frozen `Harness` per engine (its fixture, its run functions, and the calls it deliberately leaves real) and two parametrized guards comparing two **derived** sets — the engine's call graph (AST of the run functions) against what the fixture's own body actually monkeypatches (AST of its `monkeypatch.setattr` calls). They fail if a pipeline gains a call its harness neither stubs nor lists in `deliberately_real`, **and** if a harness stubs something its pipeline no longer calls. Neither side is a hand-copied list, so the guard cannot drift away from the harness it guards. Before that guard existed, a seam added to the pipeline but missed by a stub stack surfaced only as a `KeyError` in the 10:00 UTC cron.

## Key Invariants

- URL normalization (strip query params) MUST happen before hashing — this is the sole deduplication mechanism.
- `source_url` is injected into the LLM prompt so the model returns the canonical URL deterministically.
- `SUPABASE_KEY` must be the **Service Role** key (not anon) to bypass Row Level Security.
- `MAX_DAILY_SCRAPES = 180` (`run_budget.py`) — all three APIs (Serper, Firecrawl, OpenAI) are on paid-tier subscriptions. Raised from 150 on 2026-07-17 when the cap (not the deadline) became the binding limit and starved every concept/macro group. Adjust only if subscription tiers change.
- `PIPELINE_DEADLINE_SECONDS = 1800` (`run_budget.py`) — ingestion stops early if the wall clock exceeds 30 min, then flushes stats and calls `generate_macro_summary()` before returning. Raised from 600 on 2026-07-17 after the budget-efficiency fixes (PR #42): the remaining per-target cost is genuine scrape+LLM work, and full coverage of ~120 targets needs ~25–35 min. `MAX_DAILY_SCRAPES` remains the API-cost guard.
- The tail reserve (`run_budget.py`): the slot reserve is **derived per run and position-aware** — `RunBudget.concept_demand_ahead`, suffix sums of `results_per_entity` over concept targets, so at each entity target only the concept demand *still ahead* is reserved (adding concept groups or raising `results_per_entity` can't silently reopen the starvation gap; front-loaded Tier 1 concepts can't over-reserve and finish under cap); the time floor is `TAIL_RESERVE_SECONDS = 360`. When either remaining budget falls to its floor, `before_target` returns `SkipEntity` and the loop stops *starting* entity targets (logged once: "Tail reserve reached") and lets the concept/macro groups run; file order alone is no longer the only degradation policy. Entity coverage is the right thing to sacrifice — dedup absorbs day-over-day re-discoveries — while the macro groups feed the Macroeconomic Outlook and would otherwise starve silently.
- A **synthesis outage exits non-zero** (`is_synthesis_outage` → `SynthesisOutageError` → `sys.exit(1)`), and the delivery step must stay conditional on ingestion's success — **never add `if: always()`** to it in either workflow. The red job *and* the skipped email are both the alarm; a green run that stored nothing is otherwise indistinguishable from a quiet news day. The accounting-only row is still persisted before the exit, so a failed run's screening counts survive.
- The delivery window is anchored to the last **production** `delivered_at` on an earlier `run_date`, never to the delivery step's own wall clock — the wall-clock lookback (24 h; 72 h on Mondays for weekend news) is only the fallback when no delivery is recorded. `delivered_at` is stamped **after** a successful send with the run's **fetch instant**, so a failed send widens the next window instead of losing rows and a row arriving mid-run is never skipped; `fetch_since` is a strict read so a failed fetch sends nothing and stamps nothing. `delivery_window()` is pure; the Monday rule lives there.
- No `date.today()` / `datetime.now()` / `config.run_mode()` read inside an engine module: `main()` reads the run instant once (`RunInstant.current()`) and every function that needs "today" or the mode takes it — so the summary-row key (`run_date`, `run_mode`) is spelled once per run, and the write-back, the macro-summary read, the accounting row and the `delivered_at` stamp name the same row by construction. Two callee clocks stay separate on purpose because they are lookback windows, not the row key — the ZoomInfo `publishing_date_start` in `discovery.py` and the repo's 72 h `recent_headlines` window — and both read `run_instant.naive_utcnow()`, so the naive-UTC convention has one spelling. **The instant is per process**: ingestion and delivery each read their own in `main()`, so the two steps of one workflow agree on `run_date` only when the run does not straddle 00:00 UTC — always true for the 10:00 UTC cron. A manual dispatch inside the last ~30 min of a UTC day keys ingestion's row on day D (its start) and delivery's write-back and `delivered_at` stamp on D+1, where both UPDATEs are silent no-ops: the email still goes out, but the delivery accounting is lost and the next run re-sends the day. That gap pre-dates the run instant (ingestion used to key its row at finalize time, so the window was seconds rather than the ingestion duration); closing it means keying delivery's writes on the summary row it actually read, a follow-up.
- `SMTP_PASS` env var holds the **Resend API key** (legacy name retained to avoid secret rotation), read by `mailer.ResendMailer` at send time. Email is sent via the Resend HTTP API, not SMTP.
- `RECIPIENT_EMAILS` is the **only** source for the Resend `to:` list — there are no hardcoded fallbacks; `delivery_engine.send_email` reads it (with `SENDER_EMAIL`) when composing the `EmailMessage`, and the mailer adapter never touches addressing. The production workflow injects the production recipient pool; the test workflow injects `TEST_RECIPIENT_EMAILS` instead. Swapping pools is therefore a workflow-level secret change.
- Report filtering uses `americhem_impact_score` (materiality), **not** `sentiment_tag` (tone). A Negative-low-impact article is excluded; a Negative-high-impact supply disruption appears prominently. Don't conflate the two.
- `MARKET_PULSE_RUN_MODE=test` is the single switch that marks both the subject line (`[TEST]`) and the HTML body (title prefix + amber banner row). The marker is one constant, `renderer.TEST_MARKER`, which `send_email` imports for the subject. The test workflow sets it; production never does.
- ZoomInfo discovery is gated by three independent flags, all defaulting **off**: `ZOOMINFO_NEWS_ENABLED` (turns the provider on), `ZOOMINFO_RELEVANCE_GATE_ENABLED` (turns the false-positive gate on), `STORE_DISCOVERY_METADATA` (persists provenance columns — leave off until migration 003 is applied). Enabling them out of order degrades gracefully; it does not crash the cron.

## Python Conventions

- Type hints on all function signatures; `Optional[T]` for nullable returns.
- Structured logging with `%s` placeholders — never f-strings in `logger.*()` calls.
- Specific exception handling — never bare `except:` or broad `except Exception` without logging `exc`.
